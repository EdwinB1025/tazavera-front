# Corrections — refine-app-header

## Round 1

1. **The language trigger's accessible name starts with its visible code (WCAG 2.5.3 Label in Name).** Today the trigger shows `ES` while its accessible name is `Idioma: Español`, so the visible text is not part of the name and a speech user saying "click ES" may not reach it. End state: the name is the current locale's code in uppercase, then ` — `, then today's composed name. For `es` that is `ES — Idioma: Español`; for `en` it is `EN — <catalog word>: English`; for `ca` it is `CA — <catalog word>: Català`. The shell still composes the whole name and passes it to the widget as one string (design.md D6). The widget joins no text, and the visible content of the trigger (globe, code, chevron) does not change. Update spec "Language selection" (scenario "Selector is named"), design.md D6 and D10, and the AppShell composed-name test (`Idioma: Español` becomes `ES — Idioma: Español`). Every header test that queries the trigger by its accessible name keeps doing so with the new string.

2. **Picking the language that is already active does nothing.** Radix calls `onValueChange` even when the checked entry is selected again, so today the shell runs `router.push` to the same URL and adds a history entry. End state: selecting the current language's entry closes the menu and does not call `onLocaleChange`, so there is no navigation and no history entry. Selecting any other supported language behaves as today. Add a scenario to spec "Language selection" (for example "Choosing the current language changes nothing") and a test in `AppHeader.test.tsx`'s `describe("LanguageSelect")` asserting the callback is not called when the current locale's entry is chosen. The existing "calls back with the chosen locale" case must keep passing.

3. **The shell does not cast the locale when it composes the language control's name.** `AppShell.tsx` reads `LOCALE_NAMES[locale as Locale]`, which would throw on an unsupported locale; today that can't happen only because `proxy.ts` turns such prefixes into not-found pages. End state: the shell checks the locale with `isSupportedLocale` and, when it is not supported, composes the name (code and own name, per correction 1) from `DEFAULT_LOCALE` (`es`). No cast remains, and every supported locale behaves exactly as in correction 1. Record the fallback in design.md D6. Add a test that renders the shell with an unsupported locale and asserts the trigger's name `ES — Idioma: Español`, with no throw.

4. **A destructive entry in a header menu keeps its error colour on hover and focus.** On the nav surface, `hover:text-nav-text-hover` and `focus:text-nav-text-hover` override `data-[variant=destructive]:text-feedback-error`, so a destructive entry would turn to the normal hover colour. No header menu has one today, so this is latent. `feedback-error` itself fails the 4.5:1 text gate on the nav backgrounds (traditional 3.59:1 on `nav-surface` and 2.71:1 on `nav-hover`; dark 3.89:1 on `nav-hover`), so the nav surface gets its own destructive text token, built from two new primitives that keep the error hue:
   - `--color-oxblood-850: #600108` (oxblood-700 darkened) in the traditional primitives;
   - `--color-night-oxblood-450: #f27f76` (night-oxblood-500 lightened) in the dark primitives;
   - semantic `--color-nav-text-destructive`: `var(--color-oxblood-850)` in `@theme`, `var(--color-night-oxblood-450)` under `[data-theme="dark"]`.

   Measured contrasts: traditional 6.12:1 on `nav-surface`, 4.62:1 on `nav-hover`; dark 5.74:1 on `nav-surface`, 4.64:1 on `nav-hover`. `--color-feedback-error` and every existing token keep their values.

   End state: on the `nav` surface, an entry with `variant="destructive"` carries `text-nav-text-destructive` at rest, on hover and on focus; the `card` surface is unchanged and keeps `text-feedback-error`. Update design.md D2 and record the new tokens. Add a case to `DropdownMenu.test.tsx` asserting the destructive classes on the nav surface. The pairs `nav-text-destructive` on `nav-surface` and on `nav-hover` are registered as text pairs (4.5:1) in both matrices of `theme-tokens.test.ts`, and the new token is added to the guard tests' allowed sets.

## Round 2

Written by the orchestrator from Product owner's browser review of 2026-10-05 (handoff Q15 and Q16, raised from the `add-landing` worktree at 1280px). Product owner assigned both to this change and told the orchestrator to run the whole flow, taking the architect and Build roles. MVC reference: `resources/css/app.css`, `[data-flux-navbar-items]` rules. Contrast ratios were measured by the orchestrator with a script over the `globals.css` values.

1. **The header's primary navigation reads as navigation, not as inline links.** Today "Top rated" and "About us" use the shared `Link` (always underlined), sit `gap-4` from the logo and from each other, and have no hover or current treatment. End state, on medium and larger viewports (the small-viewport rule is unchanged):
   - Each entry is a nav item: no underline in any state, typography `type-navbar-item`, filling the header's height (`h-16`) with its label centred and horizontal padding of at least 1.5rem. The entries are not the shared `Link`; they keep client-side navigation and their destinations.
   - The navigation group sits at least 2rem from the brand logotype. The right group is unchanged.
   - Hover: `bg-nav-hover` and `text-nav-text-hover` (registered text pair, 4.63:1 traditional, 4.68:1 dark).
   - Keyboard focus: `focus-visible:focus-ring`.
   - Current entry: the entry whose path equals the current route's path (`/<locale>/about`, `/<locale>/offerings`, query ignored) carries `aria-current="page"` and a 2px bottom bar in `nav-indicator`, and does not take the hover fill. Register `nav-indicator` on `nav-surface` as a boundary pair (3:1) in both matrices of `theme-tokens.test.ts` (3.64:1 traditional, 3.84:1 dark). No token is added or changed.
   - `ShellChrome` already reads the path with `usePathname`; how it reaches the navigation is the architect's decision within the existing server/client split.
   Update spec "Header brand and primary navigation" (scenarios for nav-item presentation, hover and current entry), design.md, and name every existing test whose assertions change.

2. **The main area fills the viewport down to the bottom.** Today, on short pages (e.g. `/es/about`), the space below the content shows the body's default background, because the shell's root uses `min-h-full` inside the body's flex column. End state: in both themes the shell occupies at least the viewport height and the main area (`bg-surface-page`) reaches the bottom of the viewport whatever the content height. The fix lives in `src/app/shell/AppShell.tsx`; `app/layout.tsx` and the body stay as they are; no token changes. Add a spec scenario "Main area fills the viewport", update design.md, and add an `AppShell.test.tsx` case asserting the class that makes the shell's root grow to the body's height.

3. **Verification after this round.** A final task: `npm run test:run`, `npm run lint`, `npx tsc --noEmit` and `npm run build` pass, and captures at 375px and 1280px of `/es` and `/es/about` in both themes show the nav items and the filled main area.
