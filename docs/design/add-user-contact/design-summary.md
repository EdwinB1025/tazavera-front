# Design summary — add-user-contact

Generated by the design lead on 2026-10-06 (night). Sources: decisions log "contactos y locales" (2026-10-06), `add-user-account` artifacts on `feature/add-user-account` (`openspec/changes/add-user-account/design.md` D1–D11, `specs/user-account/spec.md`), the API models in `tazavera-api` (`app/Models/Contact.php`, read-only), the main specs on `develop`. The API change `add-contacts-and-locations` is not built yet (no branch in `tazavera-api` at writing time) and `contracts/openapi.yaml` on `develop` has no contacts operation: **the decisions log is the provisional contract** and every field name below is unverified until Scribe documents it. **Update 2026-10-07:** the contract on `develop` (`contracts/openapi.yaml`, `290d22e`) now documents both operations, `listMyContacts` and `createMyPrimaryContact` (§3); the provisional notes below are superseded where §3 says so.

## 0. Settled inputs (not re-decided here)

- Contacts are personal profile data, shown only to the authenticated owner, inside the account page (decisions log "contactos y locales"; Product owner's scope refinement of 2026-10-06 night, point 4: "add-user-contact stays in the profile").
- One primary contact per user; `POST` answers `409` when it already exists (decisions log).
- The account page, its session gate, its section pattern, the step-up and the form rules are `add-user-account`'s (D1 page-slice injection, D2 client checks, D6 step-up, D9 accessibility, D10 layout, D11 tokens). This change adds one section to that page and builds nothing that page already owns.
- Writes: reactive step-up (`403` → notice, the user repeats the action) and every `422` shows the generic form error (decisions log "escrituras, rutas protegidas y 422"; backlog R8).
- Forms are `noValidate` and check only what the operation's `requestBody` documents (decisions log "validación de formularios en el navegador").

## 1. Scope

A "Contact details" section in `/{locale}/account`, for every authenticated role:

1. Reads the user's contact (`GET /users/{user}/contacts`).
2. No contact → an explanatory text and an "Add contact details" action that reveals the form in the same section.
3. Submit → `POST /users/{user}/contacts`; success shows the saved data read-only.
4. A contact exists → its values, read-only.

### 1.1 Capability

`user-account` (config.yaml: "registration … and profile settings"). Delta on the requirement "Account page and its session gate" (the section list grows from four to five) plus one new requirement "Contact details". No other capability changes, except the `entities` piece of §3 (no spec of its own).

## 2. Out of scope

- Editing or deleting a saved contact: the decisions log gives only `GET` and `POST` (Open 3).
- Several contacts per user (one primary contact only).
- Coffee shop location contacts (`add-coffeeshop-location`).
- Any public display of the contact.

## 3. Contract operations (`contracts/openapi.yaml` on `develop`, `290d22e`)

| Operation | Method and path | Auth | Request | Responses used | Errors |
|---|---|---|---|---|---|
| `listMyContacts` | `GET /users/{user_ulid}/contacts`, `{user_ulid}` = session `data.ulid` | token with `profile:read` or `profile:write`, own user only (policy) | — | `data[]`: the contacts — `ulid`, `isPrimary`, `address`, `city`, `postalCode`, `country`, `phone`, `email`, `web` (nullable), `social`; the section shows the item with `isPrimary: true`; no contact → `{ data: [] }` | `401` (client chain), `403`, other → section error |
| `createMyPrimaryContact` | `POST /users/{user_ulid}/contacts` | token with `profile:write`, own user (policy; `tazavera-api` `routes/api.php` on `PROD`: `profile:write` group + `can:update,user`) | the fields, casing and required set of the operation's `requestBody` (the architect copies them from the contract; the front checks only what it documents) | `201` with `data`: the created contact | `409` exists, `422`, `403` step-up, other |

The front reads only the fields above and renders no API `message`.

### 3.1 What the interface shows per response

| Response | Shown |
|---|---|
| `GET` pending | the section card with the loading status (`LoadingStatus` of `add-user-account`) |
| `GET` 200 with a contact | the read-only contact list (§5.3) |
| `GET` 200 without a contact (`{ data: [] }`) | the empty text and "Add contact details" (§5.2) |
| `GET` network, `5xx`, other non-2xx (incl. `403`) | the section's error text and a "Try again" action that re-runs the read; the rest of the page keeps working |
| `POST` 201 | the form closes, the success status (`FormStatus`) renders above the read-only list, focus moves to the section heading (`tabIndex={-1}`) |
| `POST` 409 | the form closes, the text "You already have contact details saved." (status, not error) and the section re-reads `GET` to show them |
| `POST` 422, `5xx`, network, other | generic form-level error above the actions, values kept |
| `POST` 403 | step-up notice above the actions (`StepUpNotice`), values kept; "Confirm identity" calls `requestProfileWrite(\`/${locale}/account\`)` inside the click (user-account D6) |
| `401` anywhere | never shown; the client's chain runs; an `anonymous` end shows the page's signed-out state |

## 5. Behaviour, components, states and accessible names

### 5.1 Placement

Second section of the page: Profile, **Contact details**, Password, Security, Danger zone (Open 2). Named region labelled by its `h2` (user-account D9).

### 5.2 Empty state

Inside the section card, below the section header: the text `contactEmptyText` (`type-body`) and, 1rem below, the actions row with `Button variant="primary" size="base"` "Add contact details" (`contactAddButton`, icon `Plus` — added to `icons.ts`). Activating it replaces the text and the button with the form, and focus moves to the first field (Address).

### 5.3 Read-only details

`ContactDetails`: a `<dl>` of `LabelValueRow`s, one row per non-null value, in the order Address, Postal code, City, Country, Phone, Email, Web, Social. Values as the API returns them. Web renders as a native anchor with `LINK_CLASSES` (user-account D4), same tab, only when the value starts with `http://` or `https://`; otherwise as text (no `javascript:` or relative URL is ever a link). Email, phone and social are text. All values null → the empty state of §5.2 (nothing to show).

### 5.4 Form

`<form noValidate aria-labelledby={sectionHeadingId}>` with `ContactFields`:

| Field | `Field` label key | Input | `autocomplete` | Client check |
|---|---|---|---|---|
| Address | `contactAddressLabel` | `Input` | `street-address` | only what the contract documents |
| Postal code | `contactPostalCodeLabel` | `Input` | `postal-code` | idem |
| City | `contactCityLabel` | `Input` | `address-level2` | idem |
| Country | `contactCountryLabel` | `Input` | `country-name` | idem |
| Phone | `contactPhoneLabel` | `Input type="tel"` | `tel` | idem |
| Email | `contactEmailLabel` | `Input type="email"` | `email` | email format when non-empty (reuses `emailFormatError`) |
| Web | `contactWebLabel` | `Input type="url"` | `url` | idem |
| Social | `contactSocialLabel` | `Input` | `off` | idem |

Required markers and maximum lengths come from the contract's `requestBody` when it exists; none is assumed now. A failed check shows its message under the field, `aria-invalid`, focus to the first failing field, nothing sent (user-account D2/D9). Actions: `primary` "Save" (`save`, `type="submit"`, `loading` while pending) and `action-4` "Cancel" (`cancel`), which closes the form, discards the typed values and returns focus to "Add contact details".

### 5.5 States table

| State | Renders |
|---|---|
| session `loading` / `anonymous` | the page's own gate (user-account); the section does not render |
| reading | `LoadingStatus` with `loading` |
| read failed | `contactLoadError` (`type-body`) and `Button variant="action-4"` "Try again" (`retry`) |
| empty | §5.2 |
| form open | §5.4 |
| submitting | Save busy (`loading`), Cancel disabled |
| saved / exists | §5.3, with the success status after a `201` |

## 7. Layout and spacing (criterion A)

- Section: the section renders `AccountSection` **as it stands when this change's apply starts**, with no section styling of its own. The apply runs after `add-user-account` adopts the section card of `refine-page-surfaces` (a later small change, refine-page-surfaces Open 3 a), so the section then has that change's values: `Card variant="section"`, 1px `border-subtle` on all sides, no accent edge, `radius-container`, `shadow-lg`; a static header band on `surface-section` holding the `h2` (`type-subheading`) and the description (`type-body`) 0.5rem apart, band padding 1rem below 768px and 1rem top/bottom, 1.5rem left/right from 768px, 1px `border-subtle` at its bottom; body on `surface-card`, padding 1rem left/right/top and 1.25rem bottom below 768px, 1.5rem from 768px (refine-page-surfaces §5.3). Column width (32rem max from `md`, start-aligned) and the distance between sections are `add-user-account`'s. For reference, `AccountSection` before that adoption (user-account D10): `Card`/`CardContent` with 1.5rem padding, 2rem between sections, header `h2` + description 0.5rem apart, 1.5rem from header to content, 4px left `border-accent`, `rounded-container`; the wireframe of §11 shows this earlier card.
- Empty state: vertical stack, 1rem between the text and the actions row; no border, padding or background of its own.
- Form: vertical stack, 1.5rem between fields, between the last field and the status / step-up notice, and between those and the actions row (user-account D10). Postal code and City stay stacked at every width (the 32rem column leaves 291px inside the card at 375px, too narrow for two fields). Actions row: flex, wraps, 0.75rem gap both ways, buttons at their own width, start-aligned; Save first.
- Details: one `<dl>` with `grid gap-y-3` (0.75rem between rows), a single column at every width (the column is 32rem; `add-offering-catalog`'s two-column grid would leave under 14rem per value). Row internals are `LabelValueRow`'s (label and value at least 1rem apart, value wraps below). The success status sits 1.5rem above the `<dl>`.
- Error state: vertical stack, 1rem between the text and "Try again".
- Responsive: as the page (D10): below `md` the section padding 1rem/3rem, column full width; no horizontal scroll at 375px (long emails and URLs wrap with `break-words` on the value).
