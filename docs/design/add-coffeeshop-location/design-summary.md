## 0. Settled inputs (not re-decided here)

- Locations are created only by the `coffeeshop` role, location and contact in one transaction (`POST /locations`); `latitud`, `longitud` and `description` are optional (decisions log).
- The **front geocodes** the address with a library and sends `latitud`/`longitud`; the API never geocodes. Direction approved by Product owner: a library in the front (decisions log; orchestrator brief).
- CSP `connect-src` opened to Nominatim (OpenStreetMap) — approved by Product owner (decisions log "directorio de cafeterías").
- Coffee shop management lives in the **sidebar** with two entries, "Administrar ofertas" and "Administrar ubicaciones"; this change is the "Manage locations" page (scope refinement, point 3). `add-offering-management` round 1 point 1 leaves one entry, "Administrar ofertas"; this change adds "Administrar ubicaciones" beside it through the same entries mechanism, with no widget (decisions log 2026-10-07 "consenso, barra lateral de gestión y leyenda 1–9").
- Empty list → a message and an "add" action that reveals the form in the same view (decisions log; refinement point 3).
- Protected route: `loading` waits; `anonymous` shows a message and a "Sign in" button calling `signIn(currentRoute)` inside the click; a signed-in user without the role sees the 404 page (decisions log "rutas protegidas sin sesión: mensaje con botón" and "acceso a rutas protegidas").
- Writes: reactive step-up on `403`; any `422` shows the generic form error (decisions log; backlog R8). Forms are `noValidate` and check only what the `requestBody` documents.
- Each management area contributes its sidebar entries through the `@sidebar` slot (decisions log "entradas del sidebar de gestión"; `add-offering-management` D8). `add-specialist-evaluations` uses the shell's `entries` region instead (decisions log "filtros: preguntas de los explore", coexistence); this change follows the coffee shop area's mechanism, `@sidebar`, so both coffee shop routes use one mechanism.

## 1. Scope

Route `/{locale}/manage/locations`, for the `coffeeshop` role:

1. Lists the coffee shop's own locations (read).
2. No location → empty text + "Add location" that reveals the form in the same card.
3. With locations → the list and an "Add location" action above it that reveals the same form.
4. Submit → geocode the address once (Nominatim) → `POST /locations` with or without coordinates.
5. Sidebar entry "Administrar ubicaciones" beside "Administrar ofertas".

### 1.1 Capability

**`offering-management`**, delta with new requirements "Location management page" and "Location creation with geocoding", plus an `app-shell` delta for the CSP `connect-src` origin. Justification: `config.yaml` describes `offering-management` as the coffee shop's management area ("coffeeshop offerings (create from inventory by roaster and locations, list own …)"), the page sits in that area's sidebar next to "Administrar ofertas", and it shares its gate and entries. `user-account` was the alternative only while the locations lived in the profile, which the refinement replaced. The `config.yaml` description needs one line updated (Open 1).

## 2. Out of scope

- Editing or deleting a location, and fixing coordinates later (the API offers only `GET` and `POST`; Open 8).
- A map on this page (the directory owns the map; Open 9).
- Address autocomplete: forbidden by the Nominatim policy ("you must not implement such a service on the client side").
- Location data in `POST /register` (decisions log).

| Operation | Method and path | Auth | Request | Responses used | Errors |
|---|---|---|---|---|---|
| `listAUsersLocations` | `GET /users/{user_ulid}/locations`, `{user_ulid}` = the session user's `ulid` from `getTheAuthenticatedUser` | token with `profile:read` or `profile:write`, own user (policy) | — | `data[]`: each location with its contact details, as the operation documents them (the architect copies the field names from the contract) | `401` chain; other → list error |

## 5. Behaviour, components, states and accessible names

### 5.1 Gate

The shared protected-route gate that backlog R11 moves to `src/shared/ui` (from `add-offering-management`'s `ManagementGate`, D6) — loading, signed-out message with "Sign in", 404 for another role (Open 4, closed: R11 first).

Activating it replaces text and button with the form in the same card, which then shows its header band (§5.4); focus to the Name field.

### 5.3 List

- Toolbar above the list: `Button variant="primary" size="base" icon={Plus}` "Add location", start-aligned, on the backdrop. While the form is open the button is hidden and the form's section card renders in its place, above the list.

- List named by the page heading (`<ul aria-labelledby>`), one `<li>` per card.

### 5.4 Form

`<form noValidate>` in one **section card** (`Card variant="section"`, refine-page-surfaces §5.3): a static header band holding the `h2` `newLocationHeading` (`type-subheading`), which names the form; the fields in the body:

| Group | Field | Control | `autocomplete` |
|---|---|---|---|
| Location | Name (`locationNameLabel`) | `Input` | `organization` |
| Location | Description (`locationDescriptionLabel`) | `Textarea` | `off` |
| Address and contact | the eight `ContactFields` (Address, Postal code, City, Country, Phone, Email, Web, Social) | as in `add-user-contact` §5.4 | idem |

Groups are `<fieldset>`s with a visible `<legend>` (`type-label`): `locationGroupLegend`, `contactGroupLegend`. Required markers, lengths and formats only from the contract (`Name` is expected required; unverified). Below the fields: the geocoding note `geocodingHelp` (`type-meta`) and the attribution line (§6.3). Actions: `primary` "Save" (`save`, `loading` while geocoding or posting) and `action-4` "Cancel" (closes, discards, focus back to "Add location").

### 5.5 Geocoding behaviour (submit sequence)

1. Client checks; a failure stops here (nothing is sent anywhere).
2. If Address and City are both non-empty: **one** geocoding request with the structured fields (street, postal code, city, country), `limit=1`, aborted after 5 s (*my proposal*). Otherwise no request and no coordinates.
3. A result → `latitud`/`longitud` = its `lat`/`lon` strings as returned. No result, timeout, network error, any non-2xx (`429` included) → no coordinates (the API allows it).
4. `POST /locations` with or without the coordinates.
5. Results are cached in memory for the page's lifetime, keyed by the normalised address string, so a retry after a `422`/`403` reuses them and sends no second geocoding request (the policy's caching rule).

No geocoding while typing, no debounce needed (one request per submit; Save is busy, so a second submit cannot start). This respects the 1 request/s ceiling per user; the policy's ceiling is collective for the application, acceptable at the project's scale (policy: "moderate user bases"). The browser sends the page origin as `Referer` (default `strict-origin-when-cross-origin`; no `Referrer-Policy` is set by `proxy.ts`), which identifies the application as the policy requires.
