## 1. Scope and capability

- Change-id: folder `extract-filtered-offerings-widget` (as requested). **Proposed change-id: `extract-filtered-offerings`**: §2 places the composition in the existing `offering-list` widget rather than in a new widget slice, so "widget" in the name would point at a slice that does not exist.
- Capability: **`offering-catalog`** (backlog R12). Commits use that scope. `offering-catalog` has no main spec on `develop` yet (it arrives with `add-offering-catalog`'s archive); the delta goes against it after that merge.
- **In:** the filtered-offerings toolbar, results and sidebar facets move from the page slices into `src/widgets/offering-list` as three server compositions (§3); `OfferingsScreen` and the offerings sidebar page slice become thin callers; tests move (§5).
- **Out:** the heading block (`listEyebrow`, `h1`) stays in `OfferingsScreen` (the directory tab has its own header); `AppSidebar` framing stays in the page slice (§2); the directory itself; R9's button (§4); any change to classes, spacing, texts, queries or states.
- **Nothing the user sees or hears changes** on `/{locale}/offerings` and its sidebar, in both themes, at every width.

## 2. Placement (settled by FSD)

R12 proposes a new slice `src/widgets/filtered-offerings`. A new widget would have to import `Offerings`, `OfferingSkeletonCard`, `CATALOG_GRID_CLASSES` and `buildOfferingsQuery` from `@/widgets/offering-list`, and the sidebar composition would have to import `AppSidebar` from `@/widgets/app-sidebar`: both are widget → widget imports, forbidden by AGENTS.md ("never import … between slices of the same layer"). Therefore:

- The **body and facets compositions go into the existing `src/widgets/offering-list`** slice, which already owns the query-driven `Offerings`, its grid, skeleton and query builder. `widgets → features` (`@/features/offering-facets`) and `widgets → shared` imports are allowed.
- The **sidebar frame stays in the page layer**: the offerings sidebar page slice keeps `<AppSidebar>` and renders the widget's facets composition inside it; the directory's sidebar page slice for `/{locale}/coffeeshops/{ulid}` does the same (directory summary §4, `app/[locale]/@sidebar/coffeeshops/[ulid]/page.tsx`).

This keeps R12's intent (one composition, no copy in the directory) and its "nothing the user sees changes"; only the slice differs from the backlog's suggestion. Settled from AGENTS.md; reported to Product owner in the final note, not left open.

Where the sidebar page slice lives today: `develop` has `src/pages/offerings-sidebar` (add-sidebar-slot), while add-offering-facets D3 plans `OfferingsSidebarScreen` in `src/pages/offerings`. This change edits whichever file holds it after `add-offering-facets` merges (that change's task 0.1 reconciles the path).

## 3. The widget compositions (`src/widgets/offering-list`)

All three are Server Components (async where they read), exported with their prop types from `src/widgets/offering-list/index.ts`. Texts arrive as props from the page, which loads the catalogs (`catalog`, `landing`, `filters`) exactly as `OfferingsScreen` does today; no composition calls `getMessages` (page pattern: the screen loads, the widget renders).

### 3.1 `FilteredOfferingsToolbar`

| Prop | Type | Use |
|---|---|---|
| `searchParams` | the route's raw search params (`OfferingsQuery`) | parsed with `parseOfferingFilters` for the applied count and the sort value |
| `texts` | the toolbar texts of facets D8 (trigger, trigger with count, sort label and options) | — |

Renders `OfferingsToolbar` (`@/features/offering-facets`) exactly as facets D8 places it: a flex row that wraps, items aligned to the bottom, `gap-x-4 gap-y-3`, trigger at the start, sort at the end (`justify-between`), the sort field between 12rem and 16rem; no padding, border or radius. The page keeps placing it in the toolbar region 2rem below the heading block (`HEADER_CONTAINER_CLASSES`, `flex flex-col gap-8`).

### 3.2 `FilteredOfferingsResults`

| Prop | Type | Use |
|---|---|---|
| `locale` | `string` | — |
| `searchParams` | `OfferingsQuery` | the URL query: `buildOfferingsQuery`, then `sanitizeOfferingQuery` (facets D4) |
| `path` | `string` | the list route, for `Pagination` (`/${locale}/offerings` in the catalog) |
| `fixedQuery` | `OfferingsQuery`, optional | keys applied **after** sanitizing, overriding any same key from the URL (directory: `{ coffeeshopUlid: <route ulid> }`); absent in the catalog, so its request is unchanged |
| `texts` | `OfferingListTexts` plus `noMatches`, `clearAll`, `resultCount` (facets D9) | — |

Renders what the catalog's results `PageSection` holds today, without the `PageSection` itself (the caller keeps it, so the directory tab can place the column inside its tab panel): a `Suspense` boundary whose fallback is three `OfferingSkeletonCard`s in `@container` > `CATALOG_GRID_CLASSES` (one column, 1.5rem apart), and `Offerings` with `session` anonymous, `path`, `gridClassName={CATALOG_GRID_CLASSES}`, the sanitized and fixed query, `emptyAction` = the "Clear all" button only while a filter value is applied (facets D9: centred 1rem below "No results match these filters."), and `resultCountText`. `Pagination` keeps every query key of the URL (`tab` included for the directory), as it does today.

Values unchanged: column fills the container's content box; side margins are `PageSection`'s padding (1rem / 2rem from 768px, plus auto margins beyond 72rem), backdrop in the margins (`refine-page-surfaces` §5.5 table); cards are content cards 1.5rem apart; skeleton, empty, filtered-empty and error states in the same column.

### 3.3 `FilteredOfferingsFacets`

| Prop | Type | Use |
|---|---|---|
| `locale` | `string` | taxonomy names |
| `searchParams` | `OfferingsQuery` | parsed values for the panel |
| `texts` | the `filters` texts of facets D10 | — |

Does what facets D3 assigns to `OfferingsSidebarScreen` minus the frame: the settled coffees and taxonomy reads, the options (facets D7), the parsed values, and renders `OfferingFacets`. The page slice renders it inside `AppSidebar`'s content region, as the slot does today. The facets keep their values while the list loads or fails (separate slot), unchanged.

### 3.4 Spec delta (`offering-catalog`)

One delta is needed for `openspec validate --strict` (precedent `extract-offering-list-parts`). The observable rule this extraction makes reusable is the fixed scope: **ADDED "Filtered offerings scoped by a host"**: a view that lists offerings with the catalog's filters MAY fix query keys of the request; a fixed key SHALL override the same key in the address and SHALL never be removed by the facets, "Clear all" or paging; with no fixed key the request is the catalog's. Scenarios: fixed key overrides the address; catalog without fixed keys unchanged. No catalog requirement is modified.

## 5. Tests

- **Move to `src/widgets/offering-list/ui/`:** from `OfferingsScreen.test.tsx`, the cases about the results (skeleton fallback in one column, the list with `path`, `CATALOG_GRID_CLASSES`, the anonymous session, the toolbar slot content, the filtered empty state and the result count added by facets task 10.1); from the sidebar page slice's test, the cases about the facet reads, options and values (facets task 8.x wiring).
