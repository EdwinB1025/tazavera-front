## 2. The shared piece

### 2.1 `ClearFiltersButton` (`src/shared/ui/ClearFiltersButton.tsx`)

| Aspect | End state | Source |
|---|---|---|
| Directive | `"use client"` first statement (it calls navigation hooks and has a click handler; `client-boundary.test.ts` enforces it) | `src/shared/ui/client-boundary.test.ts` |
| Props | `label: string` — the visible text, from the host's `filters` catalog (`filters.clearAll`); `keep: readonly string[]` — the query keys that survive, passed to `clearFiltersHref` unchanged | §0.2–0.3; texts as props (`.claude/CLAUDE.md` §2) |
| Render | `Button` `variant="primary"`, default size (`base`), `type="button"`, children = `label`. No icon, no class of its own, no wrapper: the host's `emptyAction` slot places it | §0.2; `Button.tsx:23,146` (default `base`) |
| Activation | computes `clearFiltersHref(<current pathname>, <current search params>, keep)` and navigates to it with `push` and `scroll: false`, the navigation of `useFilterNavigation` (`navigateTo`) | §0.3 |
| States | rest, hover, focus-visible (shared focus ring), active: `Button`'s own; no disabled state (the host renders it only while a filter is applied) | §0.2 |
| Accessible name | the visible `label` | — |
| Business data | none: no facet key list, no route, no catalog lookup inside the component | backlog R9; `shared` is business-agnostic (fsd-architecture skill) |
| Export | `ClearFiltersButton` and `ClearFiltersButtonProps` from `src/shared/ui/index.ts` | AGENTS.md: one entry point |

Padding, margin, gap, border and radius: `Button`'s own (`base` geometry, `radius-field`, its 1px boundary from `fix-button-boundaries`); the component adds none. Spacing to the message (1rem, centred) is the host list's `emptyAction` layout (offering-facets D9), unchanged.

**Why `keep` and not "the facet keys" (backlog wording).** R9 says "taking the facet keys as a prop". The settled helper is keep-based (`clearFiltersHref(pathname, current, keep)`, offering-facets D4), and both hosts pass the sort keys, so the prop mirrors the helper and the hosts state the same array they state today. A "drop these facet keys" prop would need a second helper and would keep unknown keys that `clearFiltersHref` drops today, which changes behaviour. Settled by reuse of the existing signature (criterion C); no product decision involved.

Contrast: `Button` `primary` on the page backdrop (`surface-page`) is already gated (`refine-page-surfaces` §4.1, matrix pairs on `develop`). No new pair.

### 2.2 Spec delta (`filtering`)

A pure refactor still needs one delta for `openspec validate --strict`; the precedent is `extract-offering-list-parts` (ADDED "Pagination" for the shared piece it extracted). This change adds one requirement stating the shared action's observable behaviour, worded from the two feature requirements it serves:

- **ADDED "Clear all action for an empty filtered list"**: a host list that is empty while at least one filter value is applied MAY show a "Clear all" button with the host's text; activating it SHALL remove every query key except the keys the host keeps, SHALL remove the page, and SHALL navigate without a full reload and without moving the scroll position; the button SHALL add no text of its own. Scenarios: keeps the host's keys (`?process=washed&orderBy=cupping_avg&orderDirection=desc&page=2` → `?orderBy=cupping_avg&orderDirection=desc`); no key kept → the bare path; consumer text only.

The two feature requirements ("Filtered offerings results", "Filtered evaluation results") stay as they are: their "a 'Clear all' button with the behaviour of the panel's 'Clear all'" remains true. No MODIFIED requirement.
