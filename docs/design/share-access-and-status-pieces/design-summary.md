## 0. Settled inputs (not re-decided here)

1. Protected routes without a session show a message with a "Sign in" button in place of the content, no redirect; sign in starts synchronously inside the click (decisions log 2026-10-06; user-account spec; management spec "Access to the management area").
2. Writes use the reactive step-up: a `403` shows a notice and a "Confirm identity" action that starts the write-scope sign in inside its click; any `422` shows the generic form error (decisions log; user-account D6; backlog R8).
3. Backlog R11: move the generic gate and the status pieces to `src/shared/ui`; they take texts and callbacks, no business data; after `add-user-account` and `add-offering-management` merge; before `add-coffeeshop-location` (whose apply would otherwise write a third copy, location summary Open 4, closed). Owning capability: **app-shell** (gate) and **feedback** (status pieces). Open decision: none.
4. Texts reach components as props from the message catalogs (`.claude/CLAUDE.md` §2); icons only through `src/shared/ui/icons.ts`; `"use client"` on every `src/shared/ui` file with a handler or hook (`client-boundary.test.ts`).

- **In:** five shared pieces in `src/shared/ui` (§3); the consumers of §4 switch to them; the feature copies, their exports and their tests are removed or reduced to thin wrappers; tests move (§6).

- **Nothing the user sees or hears changes**: same elements, roles, classes, texts, focus and calls in every state of every consumer.

## 3. The shared pieces (`src/shared/ui`)

All five: no text, route, role name or API data of their own; texts and callbacks as props; exported with their prop types from `src/shared/ui/index.ts`. Types `Session` and `SessionUser` come from `@/shared/api` (shared → shared is allowed).

### 3.1 `SessionGate` (app-shell)

| Prop | Type | Use |
|---|---|---|
| `session` | `Session` | the injected session (the pages read it with `useSession` and pass it, user-account D1, management D6) |
| `loading` | `ReactNode` | rendered while `session.state === "loading"` (account: its card with `LoadingStatus`; management: `SkeletonGrid` or the disabled form; evaluations: `null`) |
| `signedOut` | `ReactNode` | rendered while `anonymous` (each consumer passes `SignedOutPrompt`, framed or not) |
| `allows` | `(user: SessionUser) => boolean`, optional | when given and false for the signed-in user, the gate renders the application's 404 (`notFound()`); absent → every signed-in user passes (account) |
| `children` | `(user: SessionUser) => ReactNode` | rendered for an allowed signed-in user |

- `"use client"` (it is rendered from client compositions and calls `notFound` from `next/navigation`; the build confirms the directive against `client-boundary.test.ts`).
- Renders no element of its own in any state: no wrapper, padding, margin, gap, border or radius. Layout belongs to what the consumer passes.
- Behaviour per state is exactly §1's: the anonymous branch never redirects; the role check uses the consumer's predicate (management `role === "coffeeshop"`, evaluations `role === "specialist"`, location `role === "coffeeshop"`), so no role name lives in `shared`.

### 3.2 `SignedOutPrompt` (app-shell)

| Prop | Type |
|---|---|
| `text` | `string` — the signed-out message |
| `signInLabel` | `string` — the button text |
| `onSignIn` | `() => void` — called synchronously inside the click (the popup must open within the activation) |

- Render: a `div` `flex flex-col items-start gap-4`: `p.type-body` (text), then `Button variant="primary"` default size (`base`), `type="button"`, text `signInLabel`. Values: column, 1rem gap, button at its own width, start-aligned; no padding, border, radius or fill (`ManagementGate` `SIGNED_OUT_CLASSES`, `EvaluationsAccess` `MESSAGE_CLASSES`).
- Account: the same visible block. Today the account's button sits in a `flex flex-wrap gap-3` row instead of `items-start`; with a single button both render it at its own width at the start of the column, so nothing visible changes. The account's `CardContent` loses its `flex flex-col gap-4` classes (the prompt carries them).
- `"use client"` (click handler).

### 3.3 `LoadingStatus` (feedback)

Moved unchanged: prop `text: string`; render and classes as §1. Server-safe (no handler, no hook): no directive needed unless the guard says otherwise.

### 3.4 `FormStatus` (feedback)

Moved unchanged: props `kind: "success" | "error"`, `text: string`; type `FormStatusKind`; render and classes as §1.

### 3.5 `StepUpNotice` (feedback)

| Prop | Type | Today (user-account) |
|---|---|---|
| `text` | `string` | `texts.stepUpText` |
| `actionLabel` | `string` | `texts.stepUpButton` |
| `onConfirm` | `() => void`, called inside the click | `requestProfileWrite(\`/${locale}/account\`)` — the route moves to the consumer |

- Render unchanged: `span` `flex flex-col items-start gap-3`; `span.type-body` `role="alert"`; `Button primary base` `type="button"`. Phrasing elements only (it still sits inside `ConfirmDialog`'s error paragraph in `DangerZone`). `"use client"`.
- The `locale` prop and the hard-coded `/account` route leave the component (route = business data): `ProfileForm`, `PasswordForm` and `DangerZone` pass `onConfirm={() => requestProfileWrite(\`/${locale}/account\`)}`; `add-coffeeshop-location` will pass `/${locale}/manage/locations` (its summary §5).

Contrast: every element keeps its current tokens on its current surface (`type-body`, `type-meta`, `type-error`, `Button primary` on `surface-card` and `surface-page`), all registered on `develop`. No new pair.

### 3.6 Spec deltas

A pure refactor still needs deltas for `openspec validate --strict` (precedent `extract-offering-list-parts`, ADDED "Pagination"). Worded from the requirements the pieces already satisfy, adding no behaviour:

- **app-shell, ADDED "Protected content gate"**: a protected view SHALL show its loading presentation while the session resolves; while anonymous, the view's signed-out message and a "Sign in" action in place of the content, with no redirect, sign in starting inside the click; for a signed-in user the route does not allow, the not-found page; otherwise the content. The gate SHALL add no text of its own. Scenarios: resolving, anonymous, not allowed, allowed, consumer text only.
- **feedback, ADDED "Request status messages"**: the loading status (polite status, spinner hidden from assistive technology and still under reduced motion, then its text); the form status (success = polite status with the hidden check icon beside its text; error = alert text, never colour alone); the step-up notice (alert text and a "Confirm identity" action that starts the write-scope sign in inside its click). Scenarios per piece; consumer text only.

The feature requirements (user-account "Account page and its session gate", "Writes and the step-up"; management "Access to the management area"; evaluations "Sign-in to the evaluation routes") stay unchanged.
